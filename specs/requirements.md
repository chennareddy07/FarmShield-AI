## 1. Project name and overview

### Project name

FarmShield AI

### Overview

FarmShield AI is a full-stack, AI-powered climate intelligence and agricultural decision-support platform designed to help farmers make informed decisions using live weather information, official meteorological warnings, agricultural knowledge, and crop-specific risk analysis. Its initial pilot will focus on Andhra Pradesh, India, supporting paddy and groundnut cultivation in English and Telugu. Farmers will be able to select their location, crop, and growth stage to receive weather insights, crop risk assessments, explainable recommendations, and relevant source references. The platform will combine live data ingestion, a deterministic agricultural risk engine, a verified agricultural knowledge base, and an AI-powered advisory assistant. Its longer-term vision includes historical climate analysis, mandi price intelligence, crop-image analysis, satellite-based insights, voice interaction, and automated alerts. The system will use a modular architecture so additional crops, regions, languages, and data providers can be added without rebuilding the application.

Application type: Responsive web application with a frontend, backend API, data-processing services, agricultural intelligence engine, and AI advisory layer.

Project maturity: Hackathon MVP designed with a scalable architecture and a roadmap toward a broader agricultural decision-support platform.

## 2. Problem statement

### Problem

Farmers face increasing uncertainty from irregular rainfall, extreme temperatures, drought, floods, cyclones, humidity changes, and other weather-related conditions. Although weather forecasts and government warnings are available through different services, farmers may still struggle to understand how a particular weather condition affects their specific crop, cultivation stage, and farming decisions.

A general weather forecast does not explain whether the forecast conditions create a meaningful risk for a paddy field during a particular growth stage or what precautions a groundnut farmer should consider. Agricultural information is also distributed across meteorological bulletins, agricultural research publications, government portals, and local advisory services. This makes it difficult to combine information into one understandable decision.

The problem is not simply a lack of weather information. It is the gap between weather information and practical agricultural interpretation.

FarmShield AI will address this gap by combining live weather observations, forecasts, official warnings, crop-specific knowledge, and explainable risk calculations. It will provide farmers with location-aware and crop-aware information in English and Telugu.

The desired outcome is that a farmer can select a location, crop, and growth stage and receive:

Current weather conditions and upcoming forecasts.

Relevant official weather warnings.

Crop-specific risk indicators.

An explanation of why a risk was identified.

Practical, evidence-supported actions.

References to the sources used.

An opportunity to ask follow-up questions through an AI assistant.

Non-goals:

The application will not replace agricultural officers, meteorologists, or government advisory services.

It will not guarantee crop protection, yield, income, or market prices.

It will not independently control irrigation systems, machinery, or farm equipment.

It will not claim that an AI-generated prediction is an official government warning.

It will not provide definitive plant-disease diagnoses from an image.

It will not initially cover every Indian state, crop, and agricultural condition.

## 6. Processing rules and business logic

### Processing logic

### L1 — Main processing pipeline

The application must follow this order:

1. Receive the farmer's location, crop, growth stage, and language.
2. Validate the input.
3. Resolve the location to latitude and longitude.
4. Retrieve live weather observations and forecasts.
5. Retrieve available official warnings.
6. Normalize units, timestamps, and source metadata.
7. Validate data freshness and completeness.
8. Load the relevant crop and growth-stage configuration.
9. Evaluate the documented crop-specific risk rules.
10. Retrieve relevant verified agricultural knowledge.
11. Construct a structured advisory context.
12. Generate the AI explanation.
13. Validate the AI output and evidence references.
14. Translate the response when necessary.
15. Return the dashboard, risk assessment, and recommendations.

If an earlier stage fails, downstream components must receive an explicit failure or incomplete-data status rather than invented information.

### L2 — Location processing

Use a geocoding service to resolve a searched location.

Store coordinates and display the resolved location name.

If browser geolocation is denied, allow manual location search.

If the selected locality cannot be resolved accurately, ask the user to select a broader supported location.

### L3 — Weather normalization

Convert provider-specific responses into a consistent internal weather schema.

Maintain:

- Original provider.
- Original units.
- Normalized units.
- Observation timestamp.
- Forecast timestamp.
- Retrieval timestamp.

Use consistent units throughout the application:

- Temperature: degrees Celsius.
- Rainfall: millimetres.
- Wind speed: kilometres per hour or metres per second, with the selected unit explicitly labelled.
- Humidity: percentage.

Never treat missing rainfall as zero rainfall.

### L4 — Data freshness

Each provider must have a configurable freshness policy.

Return:

- `fresh`
- `stale`
- `unavailable`
- `partial`

Display the retrieval time and source.

If a source is stale or unavailable, warn the user and do not describe its information as current.

### L5 — Risk-engine evaluation

The deterministic engine must evaluate only documented rules.

For each rule:

1. Check crop applicability.
2. Check growth-stage applicability.
3. Check the relevant weather variable.
4. Check the specified time window.
5. Apply the verified threshold and comparison operator.
6. Record whether the rule was triggered.
7. Attach the rule's source reference.
8. Return the resulting severity and explanation.

Example of a rule structure, not a real agricultural threshold:

`crop=paddy; stage=<verified_stage>; variable=precipitation; operator=>; threshold=<verified_value>; unit=mm; severity=<verified_severity>`

Do not implement example placeholders as actual rules.

### L6 — Overall risk classification

Return a category for each risk dimension independently.

The overall risk must be determined using a documented aggregation policy.

For the initial implementation:

- Critical triggered risk takes precedence over lower categories.
- Otherwise, the highest supported triggered severity is reported.
- If no applicable rule can be evaluated because required information is missing, return `insufficient_data`.
- If no rule is triggered and all required data is available, return `low`.

Do not calculate a numerical risk percentage unless a scientifically justified and documented scoring model is introduced.

Do not describe a rule-based classification as a machine-learning prediction.

### L7 — Crop-stage awareness

Risk rules and recommendations must be evaluated against the selected crop and growth stage.

If the growth stage is missing, do not silently assume one. Ask the user to select it or clearly return a general weather assessment without stage-specific recommendations.

### L8 — Evidence retrieval

Search the agricultural knowledge base using:

- Crop.
- Growth stage.
- Region.
- Risk category.
- Weather condition.
- Advisory topic.

Rank evidence using relevance and source quality.

Prefer current, authoritative sources.

Do not treat an unverified or outdated document as current official guidance.

Return the source metadata with every retrieved passage.

### L9 — AI advisory generation

The LLM receives:

- Validated weather context.
- Official warning context.
- Deterministic risk results.
- Retrieved agricultural evidence.
- Selected crop and stage.
- Requested language.

The LLM must:

- Explain the deterministic risk output.
- Summarize supporting evidence.
- Produce practical recommendations.
- Identify uncertainty.
- Avoid making unsupported claims.
- Avoid fabricating data, thresholds, source references, or official warnings.

The LLM must not:

- Calculate the authoritative risk classification.
- Change the risk engine's output.
- Invent a crop disease diagnosis.
- Invent a market price.
- Claim that a forecast is an observed measurement.
- Claim that an AI recommendation is an official government instruction.

If the LLM is unavailable, the application must still show weather, warnings, risk results, and evidence. Display a clear message that the AI explanation could not be generated.

### L10 — AI output validation

Use a structured output contract.

Validate required fields, language, evidence IDs, and response lengths.

Reject unsupported evidence references.

If the output is invalid, retry once with a constrained correction request. If it remains invalid, return the deterministic result and a safe fallback explanation.

### L11 — Language handling

Keep application labels in translation dictionaries rather than scattering translated strings across components.

Use English as the canonical internal language for system messages and source metadata where appropriate.

Generate Telugu responses with agricultural terminology reviewed for correctness.

Preserve numbers, units, severity, crop names, and evidence references.

### L12 — Historical analysis

Retrieve historical data from a suitable provider.

Compare selected time periods only when:

- Units match.
- Periods are valid.
- Data coverage is adequate.
- The comparison method is disclosed.

Distinguish observations from reanalysis products.

Do not claim climate change, drought probability, or long-term climate trends from a short historical period.

### L13 — Market intelligence

Retrieve actual market records from a verified provider.

Validate price dates, crop identity, units, and market identity.

Display the source and latest available date.

Never fill missing prices with estimated or fabricated values.

### L14 — Image analysis

Validate the uploaded image before sending it to a vision service.

Return possible issue categories with confidence and limitations.

Do not present low-confidence results as a confirmed diagnosis.

Require professional verification for serious or uncertain crop problems.

### L15 — Notification processing

Only create notifications for users who have explicitly enabled the relevant category and channel.

Deduplicate alerts using a stable key based on source event, location, category, and validity window.

Respect user preferences and quiet hours.

Do not repeatedly notify users for an unchanged warning.

### L16 — Satellite analysis

Use only actual satellite-derived data.

Attach observation date, provider, spatial resolution, and quality limitations.

Do not infer crop disease or exact yield from NDVI alone.

### L17 — Voice interaction

Convert voice input to text, then process it through the same validated agricultural Q&A pipeline.

Keep voice input separate from authoritative risk calculations.

Show the recognized text when possible so users can correct transcription errors.

### L18 — API and service boundaries

Keep the following responsibilities separate:

- Location service.
- Weather service.
- Official warning service.
- Agricultural knowledge service.
- Crop configuration service.
- Deterministic risk engine.
- AI advisory service.
- Market service.
- Image-analysis service.
- Notification service.
- Satellite service.
- Voice service.

Each service must have a clear input and output contract.

### L19 — Explainability

For each risk result, return:

- Triggered rule IDs.
- Weather variables used.
- Time period examined.
- Threshold source.
- Actual value.
- Severity.
- Reason in plain language.

Do not expose internal secrets, private prompts, or credentials.

### L20 — Auditability

Record non-sensitive processing metadata:

- Request ID.
- Data providers.
- Retrieval timestamps.
- Rule version.
- Knowledge document IDs.
- AI provider and model identifier.
- Processing status.

Avoid storing precise farm locations or personal details in logs unless strictly necessary and explicitly justified.

## 10. Acceptance criteria and test examples

### Acceptance criteria and test examples

A. Level 1 acceptance criteria

AC1 — Application startup

Given a correctly configured environment, when the frontend and backend are started, then the application loads and the backend health endpoint returns HTTP 200.

AC2 — Health response

Given the backend is running, when GET /api/health is called, then the response includes status, timestamp, and service availability information.

AC3 — Location search

Given a valid location query, when the user searches, then supported location results include a name and valid coordinates.

AC4 — Live weather

Given valid coordinates and an available provider, when current weather is requested, then the response contains actual provider-sourced weather data, units, source, and timestamps.

AC5 — Forecast

Given a supported location, when the forecast is requested, then the response contains available hourly and daily forecast data with valid timestamps.

AC6 — No fabricated weather

Given the weather provider is unavailable, when weather is requested, then the system reports unavailability and does not display invented values.

AC7 — Crop selection

Given the crop catalogue is loaded, when the user opens the crop selector, then paddy and groundnut are available with their configured growth stages.

AC8 — Risk assessment

Given valid weather information, crop configuration, growth stage, and verified risk rules, when the assessment runs, then each triggered risk includes its rule ID, weather input, severity, and evidence reference.

AC9 — Missing thresholds

Given no verified threshold exists for a particular risk, when the engine evaluates that risk, then it does not invent a threshold and reports insufficient information for that rule.

AC10 — Overall risk

Given applicable rules have been evaluated, when the overall risk is calculated, then critical takes precedence over lower severities, and insufficient data is returned when required data is missing.

AC11 — AI explanation

Given a validated assessment and retrieved evidence, when the advisory is generated, then it explains the existing risk results and uses valid evidence references.

AC12 — AI failure fallback

Given the LLM provider is unavailable, when the advisory endpoint is called, then the application still returns the deterministic risk assessment and a clear AI-unavailable status.

AC13 — Evidence validation

Given an AI response contains an unknown evidence ID, when validation runs, then the unsupported reference is rejected and is not shown to the user.

AC14 — Telugu interface

Given the user selects Telugu, when the dashboard is displayed, then supported interface labels and advisory text are presented in Telugu without altering numerical values or source URLs.

AC15 — Risk explainability

Given a risk has been triggered, when the user opens its details, then the system shows the reason, relevant weather variable, time period, rule, and source.

AC16 — Official warnings

Given an official warning is available, when the warning panel loads, then it displays the warning's actual source, issue time, validity, and geographic coverage.

AC17 — Warning source failure

Given official warning retrieval fails, when the warning panel loads, then it displays an unavailable state rather than generating a warning.

AC18 — Mobile responsiveness

Given a mobile viewport, when the user opens the dashboard, then the main weather, risk, and warning information remains readable and usable.

B. Level 2 acceptance criteria

AC19 — Historical data

Given historical information is available, when the user selects a date range, then the application displays the actual historical data with source and coverage information.

AC20 — Historical limitations

Given historical data is incomplete, when a comparison is requested, then the application identifies the missing coverage and avoids misleading conclusions.

AC21 — Knowledge retrieval

Given relevant verified agricultural documents exist, when an advisory is generated, then relevant passages and their source metadata are available to the AI and displayed where used.

AC22 — User profile

Given a user saves a profile, when the user returns, then saved preferences are available without making registration mandatory for other users.

AC23 — Q&A grounding

Given a user asks an agricultural question, when the assistant answers, then it uses available crop context and verified evidence, and identifies uncertainty.

C. Level 3 acceptance criteria

AC24 — Market data

Given an accessible market-data provider, when the user requests prices, then only actual returned prices are displayed with market name, date, unit, and source.

AC25 — Market data failure

Given market data is unavailable, when the market screen loads, then no fabricated price is displayed.

AC26 — Crop image upload

Given a valid JPEG, PNG, or WebP image smaller than or equal to 10 MB, when the user uploads it, then the application accepts and previews the image.

AC27 — Crop image validation

Given an unsupported or oversized image, when the user uploads it, then the application rejects it with an appropriate error.

AC28 — Image-analysis limitations

Given an uncertain image-analysis result, when the result is displayed, then the application labels it preliminary and explains its limitations.

AC29 — Notification consent

Given a user has not enabled notifications, when a risk event occurs, then no external notification is sent.

AC30 — Notification deduplication

Given the same active warning is retrieved more than once, when notification processing runs, then duplicate notifications are not generated.

AC31 — Satellite evidence

Given a satellite indicator is available, when it is displayed, then its observation date, provider, spatial resolution, and limitations are visible.

AC32 — Voice transcription

Given a supported voice recording, when transcription succeeds, then recognized text and its detected language are returned.

AC33 — Report generation

Given a valid assessment, when a report is requested, then the report contains the assessment, source references, language, and creation timestamp.

AC34 — Regional map

Given supported district-level data exists, when the regional map loads, then displayed risk layers match the underlying geographic resolution and source information.

D. Test scenarios

Scenario 1 — Successful farmer journey

Given a farmer selects an available Andhra Pradesh location, paddy, and a configured growth stage, when the farmer requests an assessment, then FarmShield AI retrieves real weather information, checks official warnings, evaluates verified crop rules, retrieves relevant evidence, and presents an explainable advisory.

Scenario 2 — Groundnut assessment

Given a farmer selects groundnut and a supported growth stage, when the risk assessment runs, then the engine uses groundnut-specific rules and does not reuse paddy thresholds without an applicable verified source.

Scenario 3 — Weather provider outage

Given the weather provider is unavailable, when the farmer opens the dashboard, then the application shows the weather service as unavailable and does not fabricate current weather or a risk assessment based on nonexistent data.

Scenario 4 — No verified agricultural evidence

Given a risk is detected but no suitable verified agricultural reference is available, when the advisory is generated, then the system explains the weather condition and explicitly states that it cannot provide a fully verified crop-specific recommendation.

Scenario 5 — AI provider outage

Given the LLM provider is unavailable, when the farmer requests an advisory, then the application still displays weather, official warnings, deterministic risk results, and available evidence without crashing.

Scenario 6 — Telugu experience

Given the farmer selects Telugu, when the farmer completes a crop assessment and opens the advisory, then the interface and supported AI explanation appear in Telugu, while measurements, dates, and source references remain accurate.

The completed project should include, as applicable:

- A functional frontend with required screens, loading/empty states, validation, and error states.
- A backend exposing documented endpoints or server actions for required workflows.
- A defined data model and persistence approach; explain demo storage if persistent storage is out of scope.
- Integration and configuration instructions for AI models and third-party services.
- Sample/demo data so the main workflow can be demonstrated without live customer data.
- Tests or reproducible checks for acceptance criteria.
- A README with prerequisites, environment setup, exact run commands for frontend and backend, test commands, known limitations, and troubleshooting.
- An `.env.example` containing variable names only, with no real secrets.

## Definition of done

The application can be started by following the README; the primary user journey works from input to output; frontend/backend integration is functional; errors are handled clearly; demo data is available; acceptance criteria can be checked; and limitations or unimplemented requirements are explicitly documented.
